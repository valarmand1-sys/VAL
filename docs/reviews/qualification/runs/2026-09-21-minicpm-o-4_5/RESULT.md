## Case B — audio perception: **not run**

The fixture exists and is correct: 22.38 s, mono, 16 kHz, generated by this
Mac's own speech synthesis with the frozen semantic content and the pauses the
definition permits, digest
`d73733aef1b12570c548b7af6c95f60c953b81373d6b2d4483565cdba39dbe2f`.

It was not run because the frozen prompt cannot be delivered through this
runtime's audio path. Two facts, both read from the code and confirmed by
running it:

- the multimodal CLI refuses the audio projector outright —
  `Failed to load CLIP model from …audio/MiniCPM-o-4_5-audio-F16.gguf`
  (`results/case_b_runtime_refusal.txt`); the audio encoder is handled by the
  fork's own omni context, not by `mtmd`;
- that omni context is a **streaming duplex speech design**. Its system prompt is
  fixed in the source ("Streaming Duplex Conversation! You are a helpful
  assistant."), the audio *is* the user's turn, and the CLI exposes no text
  prompt at all — its only input mode is `--test <prefix> <count>`, which reads
  `<prefix>0000.wav` and an optional same-named `.jpg`.

Delivering a text instruction alongside audio needs `llama-omni-server` in its
`turn_based` mode, which is a WebSocket service that would have to be built and
a client written for it. Since Case C had already decided the qualification, and
the owner's order forbids turning this into an open-ended exercise, that was not
built. **No claim of any kind is made about this model's audio capability.**

## Case C — video perception: **FAIL**

Fixture: 8 s, 640×480, one frame per second, 8 frames, digest
`23551e4a35e2298e…`. The sequence was verified frame by frame before inference:
red square left on frames 1–3, centre on 4–5, right on 6–8, blue circle present
on 7–8 and beneath the square. No text, arrow or caption anywhere in the frame.

**How the runtime actually presents video, which decided the fixture's frame
rate.** Read from `tools/server/ws_handler.cpp`: the video path shells out to
`ffmpeg -frames:v N -q:v 2` with **no sampling filter** and N capped at 8, so it
takes the **first** N frames of the file rather than N frames spread across it.
The frames are then handed to the model as one image plus extra images —
`tmp_files.image_path` and `extra_image_paths` — with no stacking and no temporal
markers in the C++ layer (a source comment says stacking is done in a Python
server, not here). At the fixture's original 10 fps the model would have been
shown the first 0.8 seconds, a stationary square, and asked about a movement it
had never seen. The fixture was therefore re-encoded at 1 fps so the runtime's
own selection spans the whole sequence — the content, duration and criteria
unchanged — and the frames were extracted with that same ffmpeg command. **What
the model received is what this runtime's video path delivers.**

Latency 23.8 s. Answer in `results/case_c_answer.txt`, verbatim:

> The video begins with several red squares scattered across a white background.
> These red squares remain in various positions throughout the initial portion.
> Later, a blue circle appears near the bottom-right area of the screen, adding a
> new element to the scene. The sequence progresses from multiple stationary red
> squares to the introduction of the blue circle.

| Frozen criterion | Result |
|---|---|
| the red square begins on the left | **not met** |
| it moves through the centre | **not met** |
| it ends on the right | **not met** |
| the blue circle appears after that movement | met — "Later, a blue circle appears" |
| the circle is beneath the square | partly — "near the bottom-right area" |

**The exact failed criterion.** The frozen definition fails a result that "loses
the cross-frame movement". This one lost it explicitly: it read the eight frames
as a single scene containing *several* red squares and called them "stationary",
rather than one square at successive positions. It also invented a central fact —
multiple squares where there is one — which is the other named fail condition.
Its internal reasoning shows it considering and rejecting movement ("maybe they
are static at first? … They might be stationary or moving slightly?").

This is a model result and not an integration artifact: the frames delivered were
the runtime's own video representation, verified to contain the full sequence.
